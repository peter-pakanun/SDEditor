# Local-first baselines and incremental server storage

Design recorded: 2026-10-08. Implementation updated: 2026-10-14.

Status: Implemented in the frontend and companion API source; production deployment and production compaction remain pending. Current StatDescription rollout requires API schema v24 before the IndexedDB v21 frontend. See [ZIP-only SD source storage](sd_baseline_storage.md) for immutable ZIP source lookup, on-demand comparisons, explicit stopped migration and the final production-copy measurement. Historical SD ZIPs are optional backup/restore dependencies; authored targets remain durable in SQLite. This document records the storage decision, implementation, migration safeguards, and local validation. It does not establish that either hosted service has been updated.

Read this document before changing managed-version baseline retention, collection/export generation, shared history storage, or database compaction. The [Workspace Status Contract](workspace_statuses.md) remains authoritative for statuses, assignment provenance, diagnostics, and export eligibility. Operational rollout instructions are in [Cloud Backup](cloud_backup.md).

## Architectural decision

The owner's SD source trust preference is **ZIP over SQLite, 10:1**: an architectural priority rather than a measured reliability ratio. The exact original ZIP plus accepted parser/duplicate decisions is the source authority. SQLite owns authored work and lifecycle records; its SD source facts are derived. Latest ZIP availability is guaranteed operationally, while historical ZIP loss is accepted. Do not introduce database source copies, extracted source artifacts or exhaustive old-ZIP checks to compensate. The [source authority and advancement model](sd_baseline_storage.md) records the managed/API versus offline/browser comparison paths and the frozen Dropped target boundary.

Keep the immutable complete parsed baseline in the browser. Manager publication retains the exact original ZIP as a separate content-addressed artifact and accepted import decisions. API v24 keeps aggregate summaries and affected-file fingerprints in SQLite, with no complete untouched source catalogs or extracted SD fragment files. Historical SD ZIP availability is optional; latest source is supplied operationally. Missing old ZIPs affect historical source comparisons and reconstruction, while authored targets and existing recovery stay durable.

The browser generates managed translated downloads from the verified original ZIP and an immutable snapshot of server-accepted Saved translations. When publication preparation or a compatibility download needs original text, the API parses the retained ZIP temporarily. Parsing is coalesced across concurrent requests and uses a bounded two-baseline memory cache; cached parses still require matching retained ZIP bytes.

Ordinary translator saves and standalone room creation do not upload full ZIPs. Unsaved drafts and existing browser-local revision history stay local. "Incremental" means sharing affected files and authored operations, rather than uploading every original file. SQLite retains real Saved text, frozen Dropped translations, provenance and authored target history; SD original source/metadata resolves only from matching ZIPs or verified client caches. Untouched target text found only in a lost old ZIP may be unavailable. Complete TM deliberately remains in SQLite. Saves are not character-level patches.

## Trusted StatDescription parsing

The 2026-10-13 update removes StatDescription membership proofs and proof-tree preparation. Browsers validate original ZIP bytes, parser/duplicate decisions, safe unique paths and source structure, and reject every incomplete staged file against its immutable English entry count before storage or upload. Original translations and accepted source identity remain separate from authored work. The API trusts the first browser-supplied original file facts, freezes their fingerprint by game/source/file, and rejects later conflicting facts. It still enforces access, bounded payloads, complete translations against accepted counts, revisions, receipts and atomic authenticated history. Managed publication and compatibility exports continue parsing retained original ZIPs; ordinary sparse saves never upload a ZIP.

New descriptors use archive version 2: `baselineId` commits ZIP SHA-256 and accepted parser/duplicate configuration without a tree root. Existing v1 descriptor roots remain identity metadata and existing IDs are unchanged. Offline reimport reuses a retained accepted descriptor, including unopened local versions. Different local import configurations require an explicit selected version rather than a guessed identity. No legacy tree is rebuilt on activation, reimport or collection download.

Pending request bodies, mutation IDs, signatures and receipts are unchanged, including historical requests containing proofs. Proof fields are accepted only as inert legacy wire data. Lost placeholder-repair acknowledgements can replay against their exact accepted event/history without changing old receipt hashes. Deletion, Dropped promotion and automatic inheritance cleanup retain their existing revision, provenance, authored-work and recovery guards; original facts are trusted rather than certified by membership.

IndexedDB v20 removes `tree`/`baselineTree` from normalized immutable baseline assets and legacy imported-baseline caches, fences older pages/workers, and does not touch history, submitted saves, outbox bodies, receipts or recovery records. API schema v22 removes obsolete proof/cache fields from mutable baseline metadata and upload preparation, reclaiming only replaced payloads that have no surviving reference. Removed proof caches are not copied into current recovery storage. Operational file fingerprints, accepted work, authored histories and frozen collection targets remain required data. Under current v24 policy, historical SD ZIPs are optional; ClientText originals and generated collection archives retain required artifact checks.

SQLite has no dedicated StatDescription proof-tree tables in the normal schema. Existing v1 root scalars and per-file fingerprints are still used, so removing proofs does not promise a large server database reduction. Run `npm run cleanup:statdescription -- --dry-run` in the API checkout to inspect a retained database. After stopping the API, `npm run cleanup:statdescription -- --stopped --compact` creates a safety backup, performs logical cleanup and vacuums free pages. Existing backups remain available for historical recovery; deployment and live maintenance are separate from local tests.

## ClientText content groups and trusted parsing

Named versions now have independent IDs and metadata. Immutable content groups belong to a version and have assigned teams: one shared StatDescription ZIP group, or one language's ClientText workbook bundle. French, German, Polish, Portuguese, Russian and Spanish default to a required normal/Gender pair; administrators can configure required roles, and explicit saved overrides remain authoritative. Existing managed versions become versions with one StatDescription group assigned to all teams, preserving their existing rooms, work and history.

ClientText uses `clienttext-trusted-v1` storage. The API retains exact original workbook artifacts, small role descriptors and initial workload summaries. It stores field identities, source/original fingerprints and original target values only for affected work, together with authored targets, reviews, provenance and server-authored history. Complete English, Developer notes, workbook layout and parsed baselines remain in the browser. New publication and saves do not build or upload a complete compact manifest, Merkle tree, original-unit witness or membership proof.

The API trusts browser parsing and derived field/workload facts. It verifies retained original bytes and immutable role/parser/group bindings, authenticates access, checks bounded payloads, and enforces revisions and mutation receipts. It does not independently certify workbook field membership or review/count calculations. The browser validates structure, duplicates, exact text, source reviews and carried alternatives against the retained originals. Dashboard summaries are accepted client-derived facts; drafts and pending operations never contribute.

Publication sends original workbook bytes, small descriptors/summaries and bounded chunks of actual carried work. Parsing, source comparison, diagnostics and workbook generation remain in the browser. Gzip remains available for substantial JSON work payloads. The API freezes accepted translations and source-only review facts at one sequence for collections; the browser produces complete workbooks from that cutoff and the original packages.

ClientText collection creation does not reread or hash workbook artifacts. Publication verifies uploaded bytes; the server freezes immutable asset hash, role, parser and group/version bindings with the accepted work. Ready means that this snapshot is durable, not that workbook bytes have been verified again or a browser output exists. The browser checks identical original identities across manifest pages, matches its cached original/parser to that snapshot and verifies exact bytes when exporting. A missing/corrupt original blocks export while the same collection ID and cutoff remain retryable. Permissions, saved-record validation, atomic snapshots, receipts and advisory ended state remain server-owned. Migration, backup/restore, actual original downloads and StatDescription/legacy archive collection verification retain their existing artifact checks.

Saved work carries stable unit IDs (role, sheet and record ID) and field-ID/value maps, not cell addresses. Export reads only those Saved/source-review unit keys from the immutable browser cache in bounded batches. Each cached field supplies its target cell, original style and source/review facts; the workbook header supplies the sheet XML path. Export workers receive only these affected units. The immutable workbook package supplies all untouched cells, including an untouched role in a paired export. Complete parsed originals stay in the browser cache; this export optimization does not change accepted facts or stored source/work/history.

Parser identity is separate from storage policy. New preparations use `clienttext-v4` for italic-header reference metadata in exports with or without localisation hints, retaining v3 blank shared-string cells and Turkish Normal/Possessive forms and v2 class variants. Accepted v1/v2/v3 groups retain their mappings and hashes. Migration preserves legacy descriptors, roots and baseline IDs as immutable identity metadata while retiring their proof requirement. It does not upgrade accepted layouts or rewrite history and frozen collections. The content policy advertises `clientTextParserVersions`; deploy an API accepting v4 before publishing newly prepared v4 workbooks. This parser extension does not add a database schema migration.

IndexedDB v14 fences earlier writers and adds a reusable immutable workbook cache keyed by original hash, parser version and role. Workspace bindings retain account/game/branch/version/group/language isolation for authored work. Identical originals can reuse parsing across versions without sharing saves or history. Legacy ready workspaces convert resumably: complete cache records become durable before their redundant per-workspace originals, compact copies and proof trees are removed. Existing drafts, history, queued command bodies, receipts and retry IDs remain intact. Ordinary saves update authored state without invalidating the cache. Cold and cached activation use the same workspace initialization screen as StatDescription.

API v19 verifies retained ClientText originals before deleting bulk manifest/upload unit rows. It preserves aggregate summaries and baseline facts for affected work, then removes only obsolete payloads that have no remaining durable reference. Original artifacts, work, history, comments, receipts, collections and their references are retained. SQLite free pages require explicit stopped compaction to reduce the live file size; normal compressed backups compact their isolated snapshot. Existing backup generations remain recovery evidence and are not pruned by this migration.

In the API checkout, `node scripts/cleanup-clienttext.js --dry-run` inventories schema 18/19 data and verifies retained originals. `--stopped --compact` requires the API to be stopped, creates a safety backup, applies the catalog cleanup and vacuums the live database. The compatible API startup also applies schema v19 cleanup; physical compaction remains explicit.

ClientText source changes retain translations with exact-source review requirements, including sparse source-only records that are not Saved work. Managed collections freeze accepted Saved units and source-only review facts; the browser reconstructs complete workbooks from verified originals, with both files in a paired download. Drafts and unaccepted outbox work are excluded. ClientText TM is a separate local projection learned atomically from valid saves and accepted shared events; its field context and retained text survive removed records. It is not sent through the legacy cloud TM endpoint.

## StatDescription inherited-save cleanup

Browser v19/API v21 require complete SD translations at every staging and new export/collection boundary. Any blank entry or English entry-count mismatch invalidates the entire present language block. Existing invalid stages are removed from active Saved work and retained as exact scoped recovery, alongside immutable history, drafts, commands and receipts. Server resets advance revisions and include recovery evidence for peers. An absent immutable selected-language tag is Missing only; a present incomplete block is Missing + Error. Full export preserves untouched absent tags without synthesizing blank blocks; new staged work must always be complete. Historical frozen collections remain retrievable. ClientText permits blank fields. Presence is derived from immutable originals or verified baseline facts, correcting existing v19/v21 counts without a schema/version bump. Deploy API v21 before browser v19.

Browser v18 and API v20 introduced cleanup of automatic inherited saves already supplied by the incoming baseline, including empty editor padding for an absent/short translation block. That older cleanup preserved explicit same-version blank saves; v19/v21 quarantine them under the complete SD policy above. Metadata-only changes with unchanged English retain complete Saved translations using current metadata and factual old/new provenance. Empty/incomplete incoming translations with nonblank predecessor text remain Dropped for comparison. Existing complete destination-version work takes precedence during reimport.

Browser cleanup is scoped, resumable and atomic; removed inherited stages retain recovery evidence. Pending commands, explicit destination saves, metadata corrections, Dropped assignments and uncertain records are protected. Shared cleanup verifies retained predecessor/current ZIPs, identical accepted per-file baseline hashes, or a pair of verified predecessor/current file witnesses with identical English and metadata, checkpoints completed rooms, and publishes revisioned staging resets. Missing/corrupt originals defer cleanup when the accepted file hashes cannot establish the baseline; history, events, receipts, original artifacts and frozen collections remain immutable. Deploy the updated API v20 first, then browser v18. The offline cleanup requires only browser v18; reload and open the affected workspace after deployment. Older initial standalone merges can receive a scoped relay of proven local inheritance plus the affected immutable predecessor file witness. The earlier provenance-relay path validates that witness against an already accepted leaf, keeps only server-authored hash pointers, and requires a matching accepted predecessor save. Explicit destination saves retain factual accepted-command provenance so the browser also preserves them. Original file witnesses remain transient; no ZIP upload or full-baseline retention is added. Prepared managed imports using the earlier carry policy must be prepared again before publication.

Standalone offline imports do not acquire a server predecessor or advance catalog HEAD. Browser cleanup discovers retained predecessor identities in the same account/game/branch/content scope and completes their verified legacy conversion before comparing staged facts. A corrupt or unfinished predecessor keeps cleanup deferred without preventing the current workspace from opening. When a first shared projection erased a normalized stage's timestamp, the language's retained edit time plus the pre-join recovery copy can establish inheritance against the chronological predecessor save; current explicit commands and later revisions still take precedence.

For an initial standalone merge, browser v18 submits a durable `/source-carry-repairs` command only after this local evidence removed the inherited stage. The API checks immutable accepted current-file facts, exact baseline text, identical predecessor English/metadata, a single R1 merge, command receipts, uploads and Dropped assignments. The owner can repair their own automatic initial merge even if the predecessor never reached the API. Another actor's merge still requires accepted predecessor baseline and Saved evidence. This operation retains history and receipts, adds no server version or ancestor, and never uploads a ZIP or local history. Rejection or newer work restores the authoritative Saved stage and records its protected revision so reload/reconnect cannot hide it or repeat the repair. Deploy this endpoint before browser v18.

## Unreachable immutable payload maintenance

Full reachability collection is explicit stopped maintenance. An earlier automatic startup implementation was reverted because it added substantial restart cost. There is no startup, request-path or background full sweep.

`npm run cleanup:sd-references -- --dry-run` inventories the configured schema-v24 database. With all API writers stopped, `npm run cleanup:sd-references -- --stopped --compact` creates a safety backup, derives compact facts from SQLite, converts SD records resumably, traces typed SQLite references, reclaims unreferenced payloads and vacuums free pages. No old ZIP checks or SD fragment installation is required. Missing/corrupt SQLite references prevent deletion. Authored targets and attribution, Dropped lifecycle, collection target cutoffs, retry identities and complete TM remain protected. See [ZIP-only SD storage](sd_baseline_storage.md) for optional source availability and backup rules.

## Persistence boundary

| Data | Browser | Server |
| --- | --- | --- |
| Complete immutable parsed baseline | Retained with accepted source identity | Temporary verified ZIP parsing only for modern managed versions |
| Original ZIP/workbooks | Local import or cached authorized download | Explicit manager publication retains external artifacts and reference/checksum |
| Accepted archive descriptor | Retained with baseline | ZIP hash/size, parser version, duplicate decisions, configuration hash and baseline identity; accepted v1 roots remain identity metadata |
| Baseline metadata | Complete local baseline | Aggregate summaries and affected-file paths, English entry counts, eligibility and source/original-target fingerprints; no complete untouched SD catalog |
| Version catalog and team state | Account-scoped cache | Independent version/group IDs, assignments, names, HEAD, deadlines, access, advisory ended state and collection references |
| Drafts and pending local saves | Durable account/workspace-scoped data | Excluded from shared state and collections before acceptance |
| Saved translations | Durable work and sync cache | Affected-file content, revisions, attribution, conflicts and idempotency receipts |
| Per-file original facts | Local baseline | Accepted compact facts for affected work; source witnesses are transient |
| Dropped copies | Separate snapshots and provenance | Frozen target text plus original source reference, compact facts, recovery generations, conflicts and assignment/resolution provenance; historical metadata resolves from ZIP/cache |
| History | Local history remains local | Authenticated authored before/after targets and attribution; untouched seed identities survive even when their ZIP-only values are unavailable |
| Modern managed collections | ZIP generated locally | Immutable Saved snapshot and verified reconstructible manifest |
| Legacy collections and rooms | Existing compatibility behavior | Required generated collection archives, authored values and seed IDs/attribution retained; v24 removes SD source manifests and untouched seed target projections |
| Dictionaries, settings, comments | Existing local/cache behavior | Existing language/account/audience contracts |

Do not persist UI status booleans. Preserve account, game, branch, version/group, baseline, selected language, role/access, and comment audience guards across asynchronous work and retries. Activating an existing version does not advance its source, create Dropped assignments, or rewrite baseline/history. Legacy publication continues to reuse matching rooms and shared history; explicit groups retain their own work identity.

## Browser translation storage

IndexedDB v9 normalizes translation data into small scoped records. Immutable accepted files are stored separately from archive assets and from staged selected-language translations. Workspace metadata, per-file factual metadata, Dropped recovery/provenance, checkpoints, shared accepted files, authored operations/conflicts, save submissions and receipts have separate stores and scope indexes. History stays in the existing revision stores, with scoped indexes. Dictionary and settings persistence retain their existing model.

An ordinary save reads its touched file's baseline/staged state and writes only the corresponding translation, history, recovery consumption, outbox and receipt in one transaction. Bulk import/export/activation can materialize a complete source or workspace, but the result is not persisted as another aggregate. Effective room-local work is derived from accepted shared files and authored operations. Persist prepared wire payloads before transmission; uncertain responses retry the same operation ID and payload. Remote event changes and their replay cursor commit together. Acknowledging a mutation cannot advance the replay cursor past unseen remote events. Equal-state updates and unchanged polling perform no writes.

Private checkpoints preserve unfinished, invalid, declined and conflicting edits; they are not required for online synchronization. They retain selected-language text and the captured base plus immutable source references, rather than duplicating a multilingual descriptor. A valid save can bypass mandatory checkpoint creation. Deferred navigation first journals a compact submitted command durably, prepares and paints the destination, then dispatches the worker. Successful commit removes that submission and consumes only its exact checkpoint revision atomically. Reload replays the original job identity and scope; newer typing and stale-base conflicts remain recoverable.

The version upgrade fences earlier writers, including v8 tabs and workers. Legacy aggregate KV records remain frozen recovery evidence. Normalization runs in resumable batches and verifies preserved content before marking a scope ready. Once ready, missing normalized records are authoritative; adapters must not resurrect deleted work from the retained aggregate. Quota errors, missing source evidence or interrupted migration preserve the original scope and prevent partial activation. Never clear browser storage or dual-write aggregates. The browser refactor keeps the existing API protocol and does not add a server migration.

## Managed collections and client ZIP generation

The modern frontend requests `format: 'manifest'` on collection/download creation. The API captures the authorized team's current server-accepted Saved files, room sequence and immutable content in one transaction. `GET /v1/collections/:id/manifest` returns that frozen text with the accepted archive descriptor, parser/encoder versions, language and download name. Later edits, drafts, pending uploads and Dropped copies cannot enter the captured collection.

Before the collection becomes ready, the API verifies the retained original ZIP, accepted baseline identity and captured export shape. The ending contract is now **durable reconstructible inputs**: a verified immutable manifest plus the retained verified original. The API marks an ending team ended after that readiness check, without waiting for a browser to finish downloading or generating its ZIP. A browser export failure retains the collection ID and snapshot for retry. Collection completion is revision-guarded so an older job cannot override a later collection or explicit reopen.

The browser uses its matching verified local baseline when available. Otherwise it downloads the original ZIP and replays the accepted parser and duplicate-block decisions without activating another workspace. It verifies ZIP SHA-256, configuration hash, baseline identity and parsed structure, without building a Merkle tree. It then replaces only the selected-language text in the captured Saved files, preserving original English, entry metadata and other language blocks. Account/source/access changes cancel stale results; explicit preparation uses the existing work spinner.

New SD collections remain Saved-only and require every accepted translation entry to be nonblank and match the English count, including unchanged complete saves. Historical frozen collections remain retrievable with their original content. They are not full-original-ZIP exports. Empty teams can end without a browser download. Download-only preserves open/ended state and the latest ending collection; recollection creates a later cutoff. Entry order, UTF-16LE encoding, fixed ZIP timestamp (2000-01-01), and DEFLATE level 5 match the API exporter. Byte equality is covered by local validation.

Compatibility is deliberate: older requests that omit `format` retain server-rendered archive collections and existing artifact downloads. The new frontend can fall back for an older API or replay a previously persisted request ID with its original request shape. Retrying uses the same durable ID. A manifest collection's legacy archive endpoint can reconstruct bytes temporarily without retaining another translated ZIP artifact. Existing archive collections are not converted or deleted.

## Counts and source advancement

`version_baselines.files` contains compact parser-derived metadata. Original completeness is represented by language-specific hashes only when every original line is nonblank and its count matches English. Hashes cover the original raw translation arrays, preserving Revised comparisons; English count and DNT eligibility preserve Missing/eligible counts. Saved, Missing, Revised and Dropped still follow the Workspace Status Contract and version-specific assignment provenance.

Source advancement uses the verified incoming ZIP and, when available, the predecessor ZIP for carry-forward and Dropped preparation. Accepted English/metadata fingerprints can preserve authored work when the old ZIP is missing; changed or unknown old English keeps that text as Dropped. Hashes cannot recreate untouched old translations. Pending preparation retains aggregate summaries and facts only for affected paths, plus necessary staged/Dropped targets and revision checks. Completed publication replaces those preparation files/teams with the accepted archive and a bounded summary. Withdrawal, recovery evidence, and source-version identities remain intact.

## Immutable payload storage

Schema v15 introduces `immutable_payloads`: canonical JSON addressed by SHA-256, losslessly deflated, checksum/size checked and protected from update/deletion. Large translation arrays and file snapshots are shared through nested references. Current state, source manifests, history, replay events, Dropped snapshots, parent captures, recovery payloads and collections can reference the same content. Decoding returns detached values; callers receive the existing wire format. Legacy inline JSON is still readable.

The v15 migration preserves row IDs, history ordering, authors, receipts, recovery IDs, resolved archives and conflict/provenance metadata. It verifies each converted payload round trip, restores immutable history/event triggers and checks foreign keys. Invalid data rolls back the migration. Reference verification traverses durable payloads, including nested frozen Dropped content. Limits bound decoding and the decoded cache. Logical room quota accounting uses original payload sizes, so compressed references do not bypass quotas.

Keep quota joins indexable: look up `immutable_payloads.hash` directly using the hash extracted from a validated reference token. Comparing a file's reference to a concatenated prefix plus every payload hash prevents an indexed lookup and scans the payload table once per room file on every save/deletion. A 2026-10-09 CPU investigation reproduced this regression with 100,000 payloads and 750 room files: the quota query consumed about 2.5 seconds of CPU; the corrected indexed query took about 0.4 ms with identical logical byte totals, including UTF-8 inline rows. A regression test checks the actual store query's plan. Queued distinct saves can sustain CPU after typing stops; retries of accepted mutations still reuse durable receipts. This fix changes the query only, requires no schema/data rewrite, and needs API deployment to affect a hosted process. The benchmark is local evidence, not a hosted profile.

Schema v16 replaced permanent managed parsed baselines and preparation duplication with compact metadata and added manifest collections. Its original preflight required every retained SD ZIP. Current schema v24 instead derives compact facts from existing SQLite source during explicit stopped conversion; missing historical SD ZIPs do not block that conversion or source-independent work. Verify ZIP identity and parser decisions when source is actually imported or reconstructed. Required ClientText workbook and generated collection dependencies retain their verification rules.

Authored target history, attribution and recovery are retained. ZIP-only conversion removes SD source and proven untouched seed projections while preserving their compact identities and attribution; missing old ZIPs can make untouched target/source values unavailable. Typed reference reclamation runs only through explicit stopped maintenance with a safety backup.

## Backups, compaction and rollout

Backups contain a compacted SQLite snapshot compressed as `sdeditor.sqlite.gz`, checksums for compressed and expanded bytes, the exact expanded size, configuration when present, and external artifact references. Format 5 marks SD source ZIPs optional; workbook originals and generated collection archives remain required, including shared hashes. Snapshot compaction never vacuums the running database. Artifact files remain excluded. Restore supports formats 1–5, verifies database integrity/references and required artifact checksums before replacing SQLite, and tolerates missing or corrupt optional SD ZIPs. `--uncompressed` creates a compact raw snapshot; databases without optional SD references retain formats 3/4.

Routine redeploy uses `backup.js --fast`: a consistent online raw snapshot with SQLite integrity/checksum checks, configuration and external artifact references. It uses format 5 when optional SD source references exist, otherwise format 3. It skips snapshot `VACUUM`, gzip and exhaustive payload decoding; the manifest records that compaction and payload-reference verification were deferred. Restore always performs full SQLite reference verification and verifies required artifact dependencies. Default manual/restore/compaction safety backups retain the compacted, compressed behavior. Raw deployment snapshots can use more disk space. `npm run test:deploy` keeps correctness/migration/recovery tests while excluding the 149,550-unit capacity fixture; full `npm test` remains the release check. Redeploy logs each stage and elapsed time so a later processing delay is attributed to its actual step.

To reclaim pages in the live database after migration, stop the API and run `node scripts/compact.js --stopped` in the API checkout. This command checks the process lock, creates a compressed safety backup, obtains an exclusive database lock, checkpoints the WAL and vacuums deliberately. It does not run automatically at startup. Retain required ClientText workbooks and generated collection archives separately in `DATA_DIR/artifacts`; historical SD source ZIPs are optional for database recovery and needed for their source-dependent reconstruction. Deploy schema v24 and compatible restore tooling before the frontend; rolling back requires old code plus a compatible database/required-artifact backup and loses post-backup writes.
